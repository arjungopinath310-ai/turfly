1 · System at a glance

Turfly is one Next.js application backed by one PostgreSQL database. The same server renders every page, answers the JSON API used by the pages and the Android app, receives Razorpay webhooks and runs the minute-by-minute background work. Everything else (payments, SMS, WhatsApp, email, push) is a third-party service called over HTTPS.

Design rules the whole system follows

  • The database is the referee. Double booking is made impossible by a PostgreSQL EXCLUDE constraint, not by application checks that two servers could both pass.
  • Only the payment gateway confirms a booking. The browser's "payment succeeded" message is recorded but never trusted; the HMAC-signed webhook is.
  • Money is integers. All amounts are stored in paise and computed on the server from database rows.
  • Time is UTC in the database, IST on screen. India has no daylight saving, so IST is a fixed +05:30 offset.
  • Every protected page and API call checks the user itself (role and ownership), not just the layout around it.

Server components and server actions

Pages run on the server, read the database directly through src/lib and send HTML. Owner and admin forms post to server actions (owner/actions.ts, admin/actions.ts), which re-check the role and turf ownership and write an AuditLog row for sensitive changes.

API routes

Interactive parts (slot picker, checkout, chat, teams) call JSON routes. Each one validates input with zod, calls requireUser(), runs domain code and turns an AppError into a clean JSON error with the right status code.

5 · Convertible pitch: how double booking is prevented

Each booking, hold or owner block writes one Occupancy row per resource unit it uses. PostgreSQL rejects any new row whose unit is the same and whose time range overlaps a live row:

EXCLUDE USING gist ("unitId" WITH =, tsrange("startAt","endAt",'[)') WITH &&) WHERE (released = false)

  • Ranges are half-open [start, end), so 6 to 7 PM and 7 to 8 PM do not clash.
  • Two players pressing "Book" at the same instant: both transactions try to insert; one commits, the other gets error 23P01 and sees "this slot was just taken". This holds even with several server instances.
  • Releasing a hold or cancelling sets released = true, which frees the units instantly without deleting history.
  • Owners can model other layouts (three 5s pitches merging into one 9s, a shared lock unit when halves can't run together) with the same tables.

Slots and prices

slots.ts builds a 1-hour grid from operating hours (late-night hours past midnight belong to the previous day), then prices each slot from the base rate and PricingRule windows (peak evenings, weekends), prorated in 30-minute pieces when a slot crosses a boundary. pricing.ts splits the price into the ₹49 online advance, optional platform fee, discount and balance payable at the venue.

6 · Sign-in

Phone OTP is the main sign-in; Google is optional when keys are configured.

  • Codes are stored only as an HMAC hash, expire in 5 minutes, allow 5 attempts and are consumed atomically (a code works once).
  • SMS abuse limits: per phone (5 per hour, 30 s between sends), per IP (10 per hour) and a global hourly cap (OTP_GLOBAL_PER_HOUR).
  • The session is a signed JWT in an httpOnly, secure cookie. Role changes take effect on the next request because currentUser() reloads the user from the database; suspended accounts are refused.

7 · Booking and payment

  • Holds: a booking starts as HELD for 5 minutes with its occupancy rows already locked, so nobody can take the slot while the player pays.
  • Order: the amount is calculated on the server from the database; an open order for the same booking is reused instead of creating another.
  • Webhook: verified with HMAC-SHA256 over the raw body (constant-time compare), stored in WebhookEvent by gateway event id so retries are no-ops, amount checked against the order, then a conditional UPDATE … WHERE status = 'HELD' confirms.
  • On confirm: ledger rows (advance collected, commission), notification jobs, in-app + push notification to player and owner.

9 · Split payments

  • Maths: the venue price after discount is split into equal whole-rupee shares. Friends pay theirs online; the organiser keeps the remainder, which their ₹49 advance already counts towards. Friends are never asked for more than the balance due at the venue.
  • Last-share race: a friend claims a share for 10 minutes while paying (FOR UPDATE SKIP LOCKED), so two people can't pay for the same one. Claims expire, so an abandoned checkout frees the share again.
  • Webhook only: a share is marked paid only by the verified Razorpay webhook. If it can no longer be paid (all taken, split stopped, booking cancelled, balance settled at the venue) the payment is refunded in full automatically. One share per person is enforced by a unique index.
  • Money: each paid share lowers balanceDue, raises splitCollected and writes a SPLIT_COLLECTED ledger row owed to the turf. Owner dashboards and analytics count it as collected online.
  • Cancellation: every paid share is refunded in full; the organiser's own advance follows the cancellation policy. The split can be changed or stopped only while nobody has paid.

10 · Background work and notifications

  • Jobs are rows in NotificationJob with a unique key per booking, template and channel, so scheduling twice never sends twice.
  • Cancelling a booking cancels its pending jobs. A failed send is retried a minute later, up to 5 attempts, then marked FAILED with the error saved.
  • In demo mode SMS, WhatsApp and email are logged instead of sent; in-app and push work normally.

11 · Chat and owner analytics

Player and owner chat

Only the player and the turf's current owner can read a conversation (admins cannot). Owners can only start chats with players who booked their turf. Names are shown, never phone numbers.

Owner analytics

analytics.ts computes revenue, bookings, cancellations, lead time, repeat customers and utilisation for any date range, compared with the previous period of the same length. Utilisation counts area-hours: a full 7s hour uses both halves (2 area-hours); owner-blocked time is excluded from capacity. Charts are dependency-free SVG (charts.tsx) with accessible table views; CSV export is formula-injection safe.

12 · Android app

  • The app shows the live website, so every website change reaches the app without a Play Store update. Only native code changes need a new build.
  • Payments: Razorpay's UPI buttons open upi:// or intent:// links, which MainActivity hands to the installed UPI app.
  • Downloads (CSV, calendar file, "download my data") go through Android's DownloadManager with the session cookie.
  • Push: with google-services.json, the app gets an FCM token; the website registers it at /api/devices; the server sends pushes with the FCM HTTP v1 API.
  • Build: mobile/scripts/build.mjs writes the server URL, syncs Capacitor, generates icons and runs Gradle → debug APK or signed release AAB.

14 · Production layout (recommended next step)

  • Domain + named tunnel: a permanent hostname such as turfly.in; the Android app and Razorpay webhook URL never change again.
  • Always-on server: a small cloud VM (or always-on mini PC) running docker-compose.prod.yml; restarts automatically.
  • Managed database with backups: point-in-time recovery protects bookings and payments.
  • Monitoring: uptime checks on /api/health and error tracking so failures are noticed before customers report them.
  • The code needs no changes for this move: only environment variables (APP_URL, DATABASE_URL, keys) differ.

15 · Value-add features (research)

Compared with Indian booking apps (Playo, Hudle, KheloMore, Turf Town) and Playtomic, the player-side features most worth adding next are split payments, slot alerts and recurring bookings. On the owner side the priorities are automatic settlement and memberships. Kerala-specific additions are monsoon rain-out credits and a Malayalam interface.
